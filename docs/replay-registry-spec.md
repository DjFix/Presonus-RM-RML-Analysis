# ТЗ: реестр replay, fixtures и исполняемых сниппетов

Статус: техническое задание, реализация и миграция не выполнены.
Дата: 2026-10-31. Версия задания: 1.

## 1. Цель и границы

Добавить в существующий операционный SQLite каталог комплектов проверки,
их файлов, исходных ELF-символов, команд и истории запусков. Автоматически
регистрировать новые комплекты при приёмке сабагентов; подключить последний
боевой тест и исторические материалы. По символу должно быть возможно найти
проверки, понять их область доказательства и воспроизвести подходящий replay.

В БД хранятся только ссылки и ограниченные метаданные. ELF, машинные инструкции,
исходники, fixtures, JSON-результаты, stdout/stderr, логи и снимки окружения
остаются по существующим путям. Не перемещать, не переименовывать и не копировать
их ради регистрации. Новые отчёты импорта и запусков создаются обычными файлами
в evidence/recovery/; scratch — только в temp/ проекта.

Регистрация не изменяет readiness, объявления, исходники, старые proof или
семантику существующих проверок. Не вводит повторное использование исторического
успеха вместо обязательных свежих проверок. Не запускает автоматически найденные
исторические команды. Не расширяет разрешение на реконструкцию или hardware.

## 2. Точки интеграции

- База определяется через `uc-library/validation/registry-sqlite/ACTIVE.json`
  и общий адаптер; для тестов обязателен явный `--db` на независимую копию.
- Текущий механизм миграций: `uc-library/tools/registry/schema.py`, Alembic,
  последняя прочитанная ревизия — `0002_workflow_indexes`. Новая аддитивная
  ревизия следует за актуальной на момент реализации; номер не фиксировать
  вслепую при параллельных изменениях.
- Модели и транзакции: существующие SQLAlchemy/`orm.Unit`, без отдельного
  неуправляемого соединения для записи и без неявного `create_all`.
- Источники символов: `catalog_symbols`, ключ `anchor`; readiness `records`
  имеет другую гранулярность `(elf, mangled)` и не заменяет точный каталог.
- Приёмка: `uc-library/tools/recovery/accept_worker.py`.
- Контракт работника: `docs/worker-handoff.md`, HANDOFF v1; изменения контракта
  версионировать и сопровождать явным адаптером v1.
- Native-индекс/Memgraph — производные потребители ссылок на комплекты;
  реестр replay не зависит от наличия запущенного Memgraph.

## 3. Модель данных

Ниже логические таблицы с префиксом `replay_`. Окончательный DDL включить в
миграцию с FK, CHECK, UNIQUE, индексами и rollback-тестами.

| Таблица | Основные поля и смысл |
| --- | --- |
| `replay_files` | `id`, SHA-256, размер; идентичность содержимого, без payload |
| `replay_locations` | `id`, `file_id`, корень/тип пути, исходный путь; несколько расположений одного содержимого и несколько версий одного пути |
| `replay_bundles` | `id`, digest нормализованного манифеста, версия контракта, task/batch/worker/session, namespace, происхождение, ссылка на исходный манифест и отчёт нормализации, время регистрации |
| `replay_bundle_files` | bundle, location/file, роль артефакта, ordinal; source/header/test/fixture/replay/proof/log/packet/producer/environment |
| `replay_bundle_symbols` | bundle, `catalog_symbols.anchor`, роль target/dependency; M:N, оригинальные варианты и ELF не схлопываются |
| `replay_commands` | `id`, bundle, kind, argv JSON-массив, cwd, timeout, digest спецификации, ссылка на описание окружения; порядок и зависимости шагов |
| `replay_runs` | `id`, bundle, уникальный attempt/request, origin live/imported, actor/session, start/end UTC, состояние; входной snapshot и описание окружения — ссылки + хеши |
| `replay_run_steps` | run, command, ordinal, status, exit code/signal/timeout, длительность, ссылки на result/stdout/stderr; отдельные значения reported/observed |
| `replay_run_symbols` | run/step, anchor, outcome и ссылка на по-символьный результат; групповой успех нельзя автоматически раздать всем символам |
| `replay_events` | append-only переходы, импорты, ошибки, проверки файлов, причины; timestamp, request, actor, ссылка на подробный receipt |
| `replay_import_items` | import request, исходный файл+hash, adapter version, состояние imported/unresolved/unsupported/error, ссылка на диагностику и нормализованный sidecar |

Состояние шага: planned/running/passed/failed/timed_out/interrupted/skipped/unknown.
Состояние регистрации не смешивать с исходом теста. Неполный historical proof
может быть зарегистрирован без права утверждать passed.

Скалярные метаданные включают oracle_kind (native_elf/pinned_provider/
source_only/unknown), вид проверки, bounded case count, время и краткий scope.
Большие описания домена, ограничений, окружения и исходные строки отчётов — во
внешнем JSON. В БД допускаются argv и небольшие списки метаданных; не допускаются
содержимое fixtures, инструкции, исходники и полные документы в JSON-колонках.
Задать и тестировать пределы размера метаданных; превышение — явная ошибка,
не молчаливое обрезание.

### Идентичности и пути

- Символ связывать по проверенному catalog anchor с ELF SHA-256, mangled name,
  адресом, размером, секцией, firmware и role. Не объединять версии по имени.
- Если historical запись содержит только ELF+имя, привязать лишь при единственном
  подтверждённом совпадении; при нескольких диапазонах оставить unresolved.
- Один файл может иметь несколько ролей, один комплект — несколько ELF/символов,
  один символ — несколько комплектов и запусков. Наличие readiness не требуется.
- Основные пути repository-relative. Исторические абсолютные пути сохранять как
  provenance; доступное текущее расположение добавлять отдельной проверенной
  связью через relocation receipt. Не переписывать исторические документы.
- Отсутствующий файл не получает выдуманный SHA. Recorded digest и digest реально
  наблюдённых байтов различать. Историческую ссылку без доступного файла хранить
  в import diagnostics; исполняемым артефактом она не считается.
- `.trashes/` не сканировать как источник исполняемых комплектов и не очищать.
  Если старый proof ссылается туда, сохранить факт ссылки/перемещения и provenance,
  не восстанавливая и не удаляя файл автоматически.

### Неизменяемость

Комплект идентифицируется digest нормализованной спецификации с входными хешами,
точными символами, командами и producer bindings. Изменение создаёт новую версию
с `supersedes`, а не перезаписывает старую. Повторный импорт тех же данных
идемпотентен. Новое реальное выполнение всегда создаёт новый run, даже с прежними
входами. Повторная публикация одного execution UUID не создаёт дубль.

Определить канонизацию JSON, порядок множеств и формат чисел/адресов; не включать
в content ID случайное время импорта. Хеш манифеста и хеш содержимого комплекта
разные: одинаковые байты JSON по разным путям сохраняют provenance расположений.

История событий и завершённых запусков append-only. Изменяемые проекции current
status допустимы только как восстановимый кэш. Удаление источника не удаляет
исторические строки. Очистка файлов и `.trashes/` вне задачи.

## 4. Автоматическая регистрация в приёмке

1. Root проверяет назначение/ownership, идентичности пакета и содержание proof,
   затем вызывает существующий `accept_worker.py` с новым каталогом результата.
2. До выполнения проверяются контракт, пути, хеши и точное согласие targets с
   запечатанным заданием. Работник передаёт данные; БД меняет только приёмка Root.
3. Нормализованный манифест, execution UUID и registration intent сохраняются
   как новые файлы. Короткая транзакция регистрирует комплект, команды и run.
4. Команды исполняются вне транзакции SQLite. Перед каждым шагом и после него
   фиксируются события/результаты; подробный вывод пишется в файлы. Зависимые шаги
   после ошибки skipped с причиной, не passed.
5. По окончании повторно проверяются входы. Изменение любого привязанного входа
   не позволяет объявить весь комплект успешно принятым. Сохраняется фактический
   результат команды и отдельный отрицательный результат проверки целостности.
6. Публикуются ссылки+хеши receipt/log/result, завершение run. Выход успеха
   возможен лишь после устойчивой регистрации. Сбой публикации — отдельный
   ненулевой исход, даже если все проверки прошли.
7. Root выполняет существующую общую интеграцию и guarded readiness admission.
   Их запуски можно зарегистрировать с собственным kind, но это не локальные
   тесты всех символов комплекта. Никакого автоматического повышения readiness.

Ошибки валидации до регистрации оформлять как rejected import/acceptance event
со ссылкой на исходный handoff и диагностикой, без фиктивного валидного bundle.
Сохранять неуспешные, timeout и interrupted запуски.

### Сбои и параллелизм

Файловая система и SQLite не образуют одну транзакцию. Нужны durable intent и
команда reconcile: повторяет только регистрацию по существующим receipts, а не
запускает команды заново. Если процесс умер без финального receipt, фиксируется
interrupted/unknown; успех не выводится из отсутствия ошибки. Оставшиеся процессы
проверяются по сохранённым handles, не перезапускаются вслепую.

Использовать существующие блокировки/guards/резервирование и короткие транзакции.
Не держать write lock во время компиляции/эмуляции. Совместить реестр replay с
guard readiness так, чтобы служебная запись запуска не меняла code generation,
не делала пакеты устаревшими и не обходила защиту readiness от гонок. Разделение
guard должно быть явно спроектировано и проверено, не предполагаться существующим.

## 6. Исторические данные

### Инвентаризация

Начать с read-only inventory и отчёта по корням:
`uc-library/candidates/`, `uc-library/validation/`,
`evidence/recovery/`, `uc-library/recovered-all/` и явно связанным пакетам в
`temp/recovery-work/`. Последний корень сканировать по ссылкам и согласованным
подкаталогам, не считать каждый scratch рабочим replay. Native bodies и raw
pseudocode регистрируются как материал анализа, а не готовый исполняемый тест.

Включить сохранённую историю macOS и дерево
`evidence/recovery/2026-10-28/vm-migration/legacy-uc-recovery/` с relocation.json.
Не выполнять исторические Mac-команды на Linux и не требовать macOS replay.
Не восстанавливать утраченные логи и не запускать массовую повторную валидацию.

Инвентаризация находит манифесты/proof/fixtures/команды и строит кандидатов через
их явные ссылки. Имена файлов — основание для discovery, не доказательство
принадлежности символу. Исключить vendor, ELF blobs, build outputs и произвольные
логи из рекурсивного импорта без подтверждённой связи.

### Адаптеры и качество

Предусмотреть адаптеры: HANDOFF v1; native trial 02; существующие validation/
proof/command receipts; fallback discovery-only. Каждый имеет версию и hash
producer, сохраняемые в receipt импорта. Не исполнять Python ради чтения метаданных
и не импортировать найденные модули. Неподдерживаемый формат остаётся в отчёте.

Для каждой находки явно указать:

- resolved/unresolved identity, достаточность provenance;
- available/missing/changed bytes, recorded и observed hashes;
- historic reported outcome и наличие проверяемого первичного receipt;
- replayability: runnable/requires_environment/analysis_only/unknown;
- причина и необходимые действия, если полноценная регистрация невозможна.

Время старого запуска неизвестно — NULL, не время импорта. Команда неизвестна —
unknown, не реконструированная строка как якобы исполнявшаяся. Успех из Markdown
без receipts — reported assertion с соответствующей силой доказательства.
Повторно использованный путь с изменёнными байтами — отдельная версия/расхождение,
не замена старой версии содержимым сегодняшнего файла.

Импорт выполнять порциями с dry-run, manifest входов, статистикой и resumable
request IDs. Дать полный знаменатель инвентаризации: imported, unresolved,
unsupported, missing, rejected. Ничего не пропускать молча; отсутствие полного
исторического охвата допустимо только с явным отчётом причин.

## 7. Интерфейсы оператора

Реализовать модуль в `uc-library/tools/registry/` и тонкий CLI. Предлагаемые
операции (это интерфейс будущей реализации, сейчас таких команд нет):

- `inventory --roots ... --out ...` — без записи в operational DB.
- `import --manifest ... --dry-run`, затем явный `--apply` с guard/backup policy.
- `list --elf ... --mangled ...`, `show --bundle ...`, `runs --bundle ...`.
- `verify --bundle ...` — проверка доступности/хешей без выполнения replay.
- `reconcile --intent ...` — восстановление регистрации без выполнения тестов.

Вывод краткий табличный и JSON; точный catalog anchor доступен как фильтр.
Запрос «последний passed» возвращает дату, provenance, входные хеши, область и
результат проверки актуальности, не один зелёный boolean. Список runnable не
означает автоматическое разрешение исполнения. Cwd/argv передаются без shell;
секреты в env/argv запрещены, сохранять имена разрешённых env и ссылки на
несекретное описание окружения. Команды — исполняемый код, не доверенные данные.

Нужны индексы: anchor→bundle; bundle→run/time; run→steps; path/hash→artifact;
import source/hash/adapter→item; уникальные request/execution UUID. Для точечного
запроса символа не перечитывать весь corpus и не хешировать все файлы. Полный
verify — отдельная операция. Замерить import/query overhead на реальных данных
и записать результаты; high-load архитектура не требуется.

## 9. Критерии приёмки

- Нет BLOB/содержимого файлов в новых таблицах; существующие файлы и sealed
  каталоги не изменены. Все расположения и provenance доступны из запросов.
- Миграция сохраняет старые строки, индексы/триггеры, readiness и catalog anchors;
  rollback при injected failure, backup и FK/integrity проверены.
- Один символ в двух ELF даёт две привязки; aliases с разными диапазонами не
  объединяются. Комплект для unreconstructed символа регистрируется без records.
- Trial 02 виден по всем трём identities; fixtures/команды/proof связаны; числа
  нативных сравнений согласованы с первичными receipts, без нового исполнения.
- Историческая инвентаризация имеет полный отчёт imported/unresolved/unsupported/
  missing/rejected; повторный импорт не добавляет дублей.
- Свежая приёмка сохраняет successful, failed, timeout, skipped, interrupted;
  ошибка регистрации не выдаёт общий success. Изменение входов обнаруживается.
- Crash до/после публикации файлов/commit восстанавливается reconcile без
  повторного replay; повторный execution UUID идемпотентен.
- Два независимых приёмщика не теряют записи и не держат SQLite lock на время
  replay; readiness admission сохраняет guards. Source generation не меняется
  от служебной регистрации запуска.
- «Последний успешный» не скрывает stale/missing inputs и imported provenance.
  Исторические абсолютные пути, relocation и неизвестные значения не подменены.
- Команды не выполняются при inventory/import/verify, malformed argv/path
  traversal/symlink escape отвергаются в исполняемом режиме. Полные логи только
  файлами; исторический оригинальный путь сохраняется даже если недоступен.
- Тесты выполняются на изолированной копии SQLite с явным override; проходят
  существующие registry/schema/workflow/acceptance/graph tests. Реальные
  import/query timings приложены без обещаний неподтверждённого ускорения.

Итоговые поставки: миграция и backup receipt; модели/CLI/адаптеры; обновлённая
приёмка и contract; тесты; inventory/import/reconciliation reports; операторская
документация с примерами запросов и явным списком исторических пробелов.
